Get started¶

This page walks through installing dadrock, starting a new DADR project, and onboarding an analysis that already has substantial code, plans, or prose. DADR can be added to any project under version control without reorganizing it.

Install¶

Prebuilt binaries (when available) install with a single command. From source:

cargo install dadrock

Confirm the binary is on PATH:

dadrock --version

New projects¶

Initialize¶

From your project root:

dadrock init

This creates:

  • decisions/ — where Markdown decision records will live;
  • a default candidate template under decisions/templates/candidate.md.

dadrock init is idempotent: re-running never overwrites an existing template or record file.

Demo¶

dadrock demo PATH is a sibling command that seeds a compact spec showcase with candidate, accepted, rejected, superseded, split, and consolidation examples. Unlike init, demo is intentionally not idempotent: it requires a new or empty decisions/ directory.

Version-control hooks¶

Hooks detect consequential analysis changes on each commit and create candidate DADRs automatically while ignoring routine, mechanical, or low-signal changes.

dadrock hooks install
dadrock hooks install --mode advisory       # default: report only
dadrock hooks install --mode create         # write candidate files (unstaged)
dadrock hooks install --mode stage          # write and stage candidates
dadrock hooks uninstall
dadrock hooks run pre-commit
dadrock hooks check --range origin/main..HEAD

The hook is an assistive guardrail. It may create candidate files and update project state. It must not accept records, block ordinary commits by default, or silently rewrite accepted DADR prose.

Modes¶

Mode Behavior Recommended use
off Hook does nothing. Projects that do not want local hooks.
advisory Report consequential changes and suggested candidates, but do not write files. Default.
create Create candidate files, leave them unstaged. Low-risk drafting.
stage Create candidate files and stage them into the current commit. Mature teams with trusted rules.
block Fail the commit when high-confidence consequential changes lack candidate coverage. Strict governance projects.

block mode should be opt-in and should support a clear bypass with an audit note.

What counts as consequential¶

A change is consequential when it plausibly affects:

  • the analysis sample;
  • outcome / treatment / exposure / covariate / construct definitions;
  • transformations, imputations, coding, derived scores;
  • joins, deduplication, linkage rules;
  • model formula, estimator, prior, hyperparameter, resampling design;
  • standard errors, tests, intervals, validation metrics, multiple-testing adjustments;
  • thresholds, cut points, inclusion rules, missingness handling;
  • robustness axes or specification families;
  • reporting, rounding, table selection, plot encoding, exported artefacts;
  • implementation, clarification, amendment, or deviation from a governing plan.

Routine changes do not create candidates by default: whitespace, formatting, lint-only edits, variable renames with no semantic change, dependency import cleanup, file moves recovered by rename detection, test fixture churn, generated-artefact timestamps, and refactors that preserve parsed operations and outputs. Routine changes may still become candidates when a #dadr/... tag, commit message, plan relation, or output difference indicates decision relevance.

Hook surfaces¶

Hook Role Default
pre-commit Inspect staged diff, optionally create candidates. Enabled in advisory mode.
prepare-commit-msg Add candidate references to the commit message when candidates were created. Optional.
commit-msg Validate manually supplied DADR trailers or candidate references. Optional.
post-commit Record hook telemetry or refresh derived state. Optional.

Hook scripts are small shims that call the dadrock binary; the logic belongs in dadrock, not in generated shell scripts. CI should run dadrock hooks check --range <range> rather than relying on a developer's local hook installation.

Existing projects¶

DADR can be bolted onto a project that already has substantial code, plans, and prose. The same toolchain that supports day-to-day authoring also bootstraps a backlog of candidates from existing artefacts and audits whether the recorded decisions match what the project actually does.

Inference¶

Inference reads one of three external anchors and produces candidates from them: the plan (SAP/PAP/preregistration), the code (source files, configs, notebooks, workflows), or the manuscript (paper, supplementary materials, dashboards). It is the symmetric counterpart to faithfulness checks: inference fills gaps by drafting; faithfulness reports gaps as discrepancies.

Inference is assistive. The system may detect, rank, draft, link, and explain candidates. A human must accept, reject, split, merge, or supersede the record before it becomes an accepted DADR.

dadrock infer --plan
dadrock infer --plan path/to/sap.md
dadrock infer --code analysis/
dadrock infer --code analysis/build_sample.py
dadrock infer --manuscript paper.qmd
dadrock infer --all                                 # all three modes, deduplicated

Common options:

dadrock infer <mode> --max-candidates 10
dadrock infer <mode> --min-confidence medium
dadrock infer <mode> --local-only                   # no remote model calls
dadrock infer <mode> --allow-remote-model           # explicit opt-in
dadrock infer <mode> --write-candidates             # write to disk; default is dry-run
dadrock infer <mode> --dry-run
dadrock infer <mode> --json

--dry-run is the safe default for first interactive use. --local-only must prevent any remote model call. --allow-remote-model requires explicit configuration when sensitive files might be included.

Plan inference¶

Reads a governing-plan artefact and produces candidates for plan items that have no implementing DADR yet:

  • parse plan headings and numbered items;
  • match each item against accepted records via #plan/<id> and #plan-relation/... tags;
  • for unmatched items, draft a candidate that summarizes what the plan asks for, with #plan/<id> and #plan-relation/implements already populated;
  • flag ambiguous plan language as #confidence/low with an ## Open questions section;
  • flag plan items that name an alternative explicitly (e.g. "either complete-case or multiple imputation") as a candidate with Alternatives drafted from the plan text.

Generated candidates carry status: candidate, an #origin/infer/plan tag, the plan section reference, and a bounded plan-text excerpt.

Code inference¶

Reads source files, notebooks, SQL, configs, and workflow definitions and produces candidates for consequential analytic choices that lack a DADR. Detection combines several signals:

  • Lexical / rule-based. Match function calls and keywords (drop_na, filter, winsor, impute, lm, glm, HC3, bootstrap, seed, primary_outcome, analysis_sample, exclude, threshold).
  • Structural parsing. ASTs, SQL parse trees, notebook cell structure, formula parsers, workflow definitions.
  • Diff-based. Compare changed code, config, plans, or workflow files; cluster changed hunks by likely decision surface.
  • Whole-repo bootstrap. Inventory analysis entry points for an initial candidate backlog.
  • Runtime state capture (opt-in). Record what executed (cell text, parameters, package versions, seed state, row counts).
  • Output-difference. Compare tables, figures, metrics, model summaries across commits.
  • Human annotation harvest. Inline #dadr/... code tags, comments, commit messages, PR review comments, issues.

Generated candidates carry status: candidate, an #origin/infer/code tag (and #origin/agent/<model> when a model was used), the source path with line range, and a bounded snippet when useful.

Manuscript inference¶

Reads the paper or rendered output and produces candidates for analytic claims that lack a DADR:

  • parse methods/results headings and per-paragraph claims;
  • detect numerical claims (sample sizes, coefficients, p-values, model summaries) and identify the analytic choices they imply;
  • detect "we did X" sentences (excluded, winsorized, imputed, fitted, clustered) and check whether each X has a matching DADR;
  • detect robustness sentences ("results are robust to ...");
  • detect figure and table captions that describe a model or sample.

Generated candidates carry #origin/infer/manuscript, the manuscript file path, and the surrounding sentence.

Candidate scoring¶

Confidence combines signal strength, number of independent source references, proximity to human rationale, magnitude of output change, plan relation, and ambiguity warnings. Recommended labels:

Label Meaning
high Clear decision surface, strong source signals, plausible alternatives, low ambiguity.
medium Likely decision but missing rationale, alternatives, or full context.
low Weak signal, useful for triage but not ready as a draft.

Confidence is captured as a #confidence/<level> tag on the candidate.

Privacy and minimization¶

Inference must follow data minimization:

  • store paths, fingerprints, summaries, and bounded snippets by default;
  • avoid storing raw data values unless explicitly enabled;
  • redact secrets and person identifiers where feasible;
  • allow project-level denylist / allowlist rules;
  • keep runtime capture opt-in;
  • record whether source excerpts were sent to a remote model;
  • preserve enough provenance to audit model-assisted drafts.

Sensitive projects should run --local-only with no remote model calls.

Code-tag scan¶

Authors can annotate analysis code directly with #dadr/... tags in source comments. Tools collect these tags into a code-tag report, link them to records, and use them as signals for candidate drafting and faithfulness checks. The full convention is documented in the format spec; the relevant invocation is:

dadrock generate code-tags                   # the code-tag table report

#dadr/<uuid7-prefix> tags link the surrounding code to a specific record. #dadr/kind/..., #dadr/scope/..., #dadr/topic/..., #dadr/axis/..., etc. classify the surrounding code without naming a specific record (useful when the relevant DADR doesn't exist yet — these become candidate seeds for dadrock infer --code). #dadr/ignore suppresses candidate generation for the surrounding code.

Faithfulness¶

Once a stable trace of accepted records exists, three symmetric checks compare it to other artefacts of the analysis. They are the readout side of inference: where inference fills gaps by drafting candidates, faithfulness reports gaps as discrepancies for human triage.

Check What it compares
Plan faithfulness Records vs. SAP / PAP / preregistration / cleaning plan
Code faithfulness Records vs. code, configuration, notebooks, workflow files
Manuscript faithfulness Records vs. manuscript or rendered output

Each check is read-only. Each produces a structured discrepancy report. Each lists candidate fixes (a record needs to be added, an existing record needs to be superseded, or the artefact needs to be amended). None of them ever mutates a record.

dadrock faithfulness --plan
dadrock faithfulness --plan path/to/sap.md
dadrock faithfulness --code
dadrock faithfulness --code analysis/
dadrock faithfulness --manuscript paper.qmd
dadrock faithfulness --all                       # all three, single combined report

Common options:

dadrock faithfulness <mode> --json
dadrock faithfulness <mode> --fail-on error      # CI-friendly exit codes
dadrock faithfulness <mode> --out path/to/report.md

Plan faithfulness¶

Compares accepted DADRs against a governing-plan artefact (Statistical Analysis Plan, Pre-Analysis Plan, preregistration, study protocol, data cleaning plan).

  • parses plan headings and numbered items;
  • maps each item to zero or more accepted records via #plan/<id> and #plan-relation/... tags;
  • flags plan items with no implementing record (gaps);
  • flags records that claim #plan-relation/implements but reference a plan item that doesn't exist (orphans);
  • flags records that contradict a plan item (drift);
  • separates deviations (#plan-relation/deviates-from) from gaps and orphans, since they are an expected part of analysis.

Each deviation must include a ## Plan deviation section with reason, impact assessment, and reviewer (validation enforces this; see dadrock).

Code faithfulness¶

Compares accepted DADRs against the code, configuration, notebooks, and workflow files that implement the analysis.

  • builds the set of accepted records;
  • builds the set of analytic activities present in the source tree (using the project's tag vocabulary and conventions described in Tags);
  • maps each activity to zero or more records via #dadr/<uuid> code tags, structural matches, and tag overlap;
  • flags activities with no governing record (gaps);
  • flags records with no implementing activity (orphans);
  • flags records that contradict the activity (drift) — for example, a record specifying a complete-case rule when the code path implements multiple imputation;
  • flags stale #dadr/<uuid> code tags that point at non-existent records.

Code faithfulness is the largest mode in practice. It is most useful immediately after major refactors, before submission, and on every PR via CI.

Manuscript faithfulness¶

Compares accepted DADRs against the paper, supplementary materials, dashboard, or other rendered output.

  • parses methods/results section headings and per-paragraph claims;
  • detects numerical claims and identifies the analytic choices they imply;
  • detects "we did X" sentences (excluded, winsorized, imputed, fitted, clustered) and checks whether each has a matching DADR;
  • detects robustness sentences and checks whether each robustness check has a matching record;
  • flags manuscript claims with no governing record (gaps);
  • flags records that contradict a manuscript claim (drift);
  • flags boilerplate prose ("we used standard methods") as a #confidence/low candidate signal rather than a hard gap.

Discrepancy report¶

A faithfulness report has a consistent shape across the three modes:

Faithfulness: code (analysis/)

  ─ gaps
    [analysis/build_sample.py:42-58] sample-filter activity has no record
    [analysis/build_sample.py:71]    deduplication activity has no record

  ─ orphans
    [01938c20a3b4] references analysis/build_sample.py:88 (file deleted)

  ─ drift
    [01938c1f9d12] specifies complete-case; code path implements multiple imputation
                   (analysis/impute.py:14)

  ─ deviations
    [01938c30b1f0] #plan-relation/deviates-from #plan/SAP-2.1
                   reviewer: jdoe; impact: documented in body

7 issues found (2 gaps, 1 orphan, 1 drift, 1 deviation, 2 informational)

The report is grouped by category, severity-labelled, and link-rich.

CI integration¶

- name: Code faithfulness
  run: dadrock faithfulness --code --json --out report-code.json --fail-on error

- name: Plan faithfulness
  run: dadrock faithfulness --plan --json --out report-plan.json --fail-on error

- name: Manuscript faithfulness
  run: dadrock faithfulness --manuscript paper.qmd --json --out report-manuscript.json

Most projects start with code faithfulness only, in non-failing mode (--fail-on never). Plan and manuscript modes are enabled once the trace is rich enough to make their reports actionable.

Faithfulness checks are diagnostic, not authoritative. The records remain the canonical statement of what the analysis decides; the artefacts (plan, code, manuscript) are checked against them. When a check reports drift, the right response is usually to draft a new candidate, accept it, and link it as superseding the old accepted decision, not to silently rewrite the prior record. See the immutability rules in the DADR specification.
